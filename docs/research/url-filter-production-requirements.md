# iOS 26+ URL filter production requirements

Checked 2026-11-22. Scope: Network Extension URL Filter, `NEURLFilterManager`, and `url-filter-provider`, including changes Apple currently documents for iOS and macOS 27.3. Those 27.3 changes are described as upcoming, not already enforced on shipping releases. This report uses Apple's documentation, WWDC transcripts, and Apple-owned source repositories. The repository's probe report is cited separately as local observation.

## Findings

1. **App Store distribution is a documented use of the entitlement, but production service approval is a separate gate.** The entitlement JSON explicitly includes `url-filter-provider`. Its discussion says, "To add this entitlement to an App Store app, enable the Network Extensions capability in Xcode." WWDC25 separately requires Apple approval of the OHTTP server configuration before App Store, TestFlight, ad hoc, Developer ID, or enterprise distribution. These sources do not establish an additional, separate manual application for the entitlement value itself. Actual distribution provisioning for this project's team remains untested. [E1], [W25, 19:29-20:07]
2. **The production design includes an Apple-hosted OHTTP relay and an operator-hosted gateway, PIR service, and Privacy Pass issuer.** Current registration is through **Identity & Trust in CloudKit Console**, not an old standalone request-form link. Apple's onboarding checklist requires a working service, gateway resources, issuer and service URLs, test data, a validation bearer token, DNS ownership proof, and traffic estimates. HTTP/2, HTTPS, standard ports, and host-based service URLs are production concerns that the LAN probe did not exercise. [O1], [U1], [I1], [W25, 18:51-20:07]
3. **Development success does not establish production readiness.** WWDC25 explicitly exempts development-signed builds; onboarding describes bypassing the relay when installed directly from Xcode and allowing local HTTP, custom ports, and paths. No inspected primary source identifies the exact internal `get-task-allow` test. A Swift `DEBUG` compilation condition is not the documented exemption. [O1], [W25, 20:04], [C1]
4. **Apple explicitly describes an off-device PIR database.** The sample's `localhost:8080` address means a server on the Mac running the macOS sample. For an iOS client Apple instead specifies the Mac's LAN IP. A production service must be reachable through Apple's approved relay/gateway arrangement. An entirely on-device PIR service is not established as supported by these sources; the conclusion that ordinary device loopback cannot replace the production server follows from the documented network topology, rather than an explicit Apple sentence banning every on-device implementation. [U1], [S2], [O1], [W25, 12:37-13:23]
5. **Installing a filter requires consent and a device password; later disabling it is explicitly available in Settings.** Apple's sample does not state whether the later Settings disable action requires a password. The local probe observed one-tap disable inside the app without a passcode. Family Controls child authorization has app-removal protection, while individual authorization explicitly lacks that implicit protection. Neither statement establishes that Family Controls locks the separate URL filter switch. [S1], [F1], [W22], [L1]
6. **Apple publishes useful PIR sizing examples, not a production capacity promise.** One tuning example has a 28.2 KB query, 22.6 KB response, 680.8 KB evaluation key, and about 51 ms server runtime for 100,000 two-byte rows. It does not identify the hardware or call that runtime CPU time. The URL sample's 50,000 entries per shard is an example parameter. Upcoming 27.3 requirements impose a power-of-two shard count and a 65,536-shard maximum for NEURLFilter. The service README expressly warns against running the example in production. [P1], [P2], [T1], [V1], [R1]
7. **The public sources support consumer, parental-control, school, and enterprise uses, but do not settle every approval boundary.** The VPN organization-account rule is specifically worded for apps offering VPN services and using `NEVPNManager`; it is not sufficient evidence of an organization-only NEURLFilter rule. Individual-developer production eligibility, a closed list of permitted filtering categories, and a country-by-country relay availability policy remain unverified. [W25, 11:18-11:40 and 25:43], [G1, 5.4-5.5], [A1], [O1]

Evidence labels below distinguish **requirement** from **documented behavior**, **sample default/example**, **published example measurement**, **inference**, **local observation**, and **unknown**. "Unknown" means the sources checked do not establish the answer; it does not mean Apple has no such rule. All source labels resolve to exact URLs in the source register.

## 4. Localhost or on-device PIR versus a remote service

| Question | Finding and evidence classification | Source URLs |
|---|---|---|
| What does Apple explicitly place on device and off device? | **Explicit architecture.** URL filters overview: "Network Extension performs URL filtering on your behalf with your URL data set, using both the Bloom filter on the device as well as an off-device database hosted on your Private Information Retrieval (PIR) server." WWDC says the app and extension do not execute in the filtering path. | [URL filters JSON][U1]; [WWDC25 at 12:37][W25-topology] |
| Does Apple's localhost example mean a server on the iPhone? | **No, in the documented example.** The setup article says to build/run the sample on **macOS** and use `http://localhost:8080`. It then says, "If you run the app on iOS instead, use your Mac's IP address in the URL." The sample server listens on loopback by default and allows binding all interfaces for LAN tests. These are development instructions for a Mac-hosted server. | [PIR setup JSON][S2]; [NEURLFilter server testing instructions][T1] |
| Can ordinary device loopback replace the production server? | **Inference, not a universal prohibition quote.** The Apple relay forwards to an approved operator gateway, which must forward to the PIR service. Ordinary iPhone `localhost` denotes that phone only and is not an endpoint Apple's remote relay can directly reach. Combining this network fact with Apple's topology gives no supported production plan consisting only of a listener on each user's loopback. These sources do not explicitly prove every conceivable on-device gateway/tunnel arrangement impossible, or document such an arrangement as supported. | [Onboarding][O1]; [WWDC25 at 18:51][W25-relay]; [PIR-server API JSON][M3] |
| Must the PIR compute process itself have a public IP? | **Not established as a requirement.** Apple requires a reachable approved OHTTP gateway and working service; the gateway forwards to the target resource. **Inference:** compute could sit behind that gateway on a private network. Approval of a particular private-backend deployment remains **unverified**. | [Onboarding][O1]; [WWDC25 at 17:50-18:20][W25-ohttp] |
| Can a local Bloom filter decide every positive match? | **Documented behavior.** Bloom negatives allow immediately. A positive is inconclusive and may need an off-device PIR lookup for a final verdict. Serving a Bloom filter from the app bundle avoids a filter-download service, not the PIR architecture. **Local observation:** with the server down and fail-open selected, all six never-seen listed sites tested loaded; previously queried matches stayed blocked. Fail-closed blocked five never-seen listed sites while three controls loaded. Cache lifetime is still unknown. | [URL filters JSON][U1]; [WWDC25 at 14:29][W25-bloom]; [local probe][L1] |
| Is fail-closed an offline replacement for the server? | **Inference.** Failing closed handles lookup errors; it does not turn a possibly-positive Bloom match into an authoritative database result. The probe shows useful availability behavior, not a production exemption from operating/registering the service. Apple sample instructions toggle Fail Closed on; this is separate from a guarantee of offline exact filtering. | [Sample JSON][S1]; [fail-closed API][FCLOSE]; [local probe][L1]; [onboarding][O1] |

## 6. Query size, CPU, database capacity, sharding, hardware, and token issuance

| Question | Finding and evidence classification | Source URLs |
|---|---|---|
| What small-value PIR numbers does Apple publish? | **Published illustrative example, not an SLA.** ParameterTuning says, "Say we run `PIRProcessDatabase`" for 100,000 rows with two-byte values, RLWE `n_4096_logq_27_28_28_logt_4`, one shard. It lists evaluation key **680.8 KB**, query **28.2 KB**, response **22.6 KB**, and server runtime **about 51 ms**. These are not stated to be production NEURLFilter measurements or end-to-end network latencies. | [Parameter tuning source][P1] |
| What is the bandwidth/compute trade-off? | **Published illustrative examples.** With one cuckoo hash function, the same section gives an **11.3 KB** response and **about 65 ms** server compute time. A wide-database example has 1,000 rows of 60,000-byte values: **738.3 KB / 610 ms**, then **387.2 KB / 840 ms** after changing RLWE parameters. One hash function can push runtime to **about 3.5 seconds**. URL membership values are much smaller; the wide example is context, not a URL-filter sizing estimate. | [Parameter tuning source][P1]; [NEURLFilter data format][DATA] |
| Are these CPU time, QPS, or a hardware recommendation? | **Unknown.** The tuning page calls the figures server runtime/compute time; it does not identify processor, core count, memory, network, concurrency, or CPU-seconds accounting. Do not claim a specific CPU budget, reciprocal-QPS capacity, hosting price, or latency percentile from them. The checked benchmark entry source runs both single-threaded and multithreaded variants, which further prevents treating a single unqualified number as a fleet-sizing guarantee. No new benchmark was run for this report. | [Parameter tuning source][P1]; [benchmark entry source][BENCH] |
| What is the documented database ceiling? | **Capability statement plus unknown.** URL-filter overview says it supports "filtering millions of URLs". Neither that phrase nor the ten-row demo establishes a hard maximum record count, byte size, or resident-memory budget. A universal database/Bloom-filter size ceiling is **unverified** in the sources checked. Upcoming shard-count limits are a real bound on configuration shape, not a published maximum entries-per-shard. | [URL filters JSON][U1]; [server testing instructions][T1]; [OS changes][V1] |
| What does sharding cost or reveal? | **Documented property.** "Keyword PIR's server runtime is linear in the shard size, independent of the keyword size, and dependent on the value size." More shards improve runtime but reveal which shard the client requested and increase configuration information. Reusing PIR parameters can reduce configuration size. Treat shard selection as a privacy/performance trade-off, rather than claiming perfect concealment of all query metadata. | [Parameter tuning source][P1]; [database processing source][P2] |
| Is 50,000 entries per shard mandatory? | **Sample parameter only.** TestingInstructionsNEURLFilter uses `entryCountPerShard: 50000`, five trials per shard, and `n_4096_logq_27_28_28_logt_5`, while expressly directing readers to tune parameters. It is neither a maximum nor a minimum production requirement. The database tool supports setting shard count or entry density and optional constraints. | [Server testing instructions][T1]; [database processing source][P2] |
| What shard limits are actually specified? | **Upcoming NEURLFilter requirement, 27.3.** At most **65,536 shards** and a **power-of-two** shard count. Devices reject invalid counts. OSChanges says these changes are not yet enforced on shipping releases. A test profile for 27.2 betas can activate the listed changes early except fetching config through Apple infrastructure. The latter remains postponed. The 65,536 limit is not a statement that a URL dataset may contain only 65,536 entries. | [OS changes][V1] |
| What hardware does Apple specify? | **Example build requirements.** `pir-service-example` README lists a **64-bit, little-endian processor**, **macOS or Linux**, and **Swift 6.1+** to build the sample. The current HE README maps `main` to **Swift 6.2+ / Xcode 26+** and stresses `-cross-module-optimization` for performance. The sample container tutorial's macOS 26 requirement belongs to Apple's `container` tool, not a universal PIR hosting requirement. Mandatory Apple Silicon, a GPU, a particular cloud, RAM size, and minimum production instance class are **unverified**. | [Service README][R1]; [HE README][HE]; [container-based setup JSON][S2] |
| How expensive is evaluation-key management? | **Published size and protocol requirement.** The 680.8 KB number is an example key size, not necessarily per lookup. Existing endpoints upload keys ahead of queries; upcoming 27.3 queries can carry a fresh evaluation key inline when unused pre-uploaded keys run out. A real service should persist uploaded keys. Request-size estimates for registration should account for the supported protocol/version mix; no universal total bytes per lookup is inferred. | [Parameter tuning][P1]; [HTTP endpoints][H1]; [common errors][ERR]; [OS changes][V1] |
| What Privacy Pass issuance workload is documented for 27.0+? | **Version-specific documented behavior.** Tokens last **one week**. Keep each public verification key valid for **at least one week after its last use** for issuance. Proactive refill runs approximately every **six hours**, with up to about **one hour of random jitter**, while idle and connected. Its batch is `max(1, round(dailyRate * 6 / 24))`, using a consumption average with a **seven-day half-life**, capped at **512** tokens per run. Cold starts begin at one per proactive run; initial registration also has a ten-token warm-up. These details must not be projected backward onto iOS 26. | [Authentication, token-fetching section][AUTH]; [OS changes][V1] |
| What happens during bursts or token exhaustion? | **Version-specific documented behavior, 27.0+.** Fewer than **five** unused tokens triggers one reactive refill, delayed randomly **0-2 hours**, requesting a fixed **ten** tokens for each user token below the threshold. When a live PIR request has no token, the system fetches **one synchronously and nine in the background**. Fixed batches avoid revealing cache state through batch size. These are client issuance schedules, not server rate-limit promises or measured RSA signing capacity. Numerical issuer CPU/QPS benchmarks are **unknown**. | [Authentication][AUTH] |
| Does user-tier support continue unchanged? | **Upcoming NEURLFilter behavior, 27.3.** Clients stop calling `/token-key-for-user-token` and choose the first valid directory key. The endpoint remains relevant for older clients. Do not confuse changes in current sample config format with proof that every already-shipping OS has stopped using the old endpoint. | [Authentication][AUTH]; [HTTP endpoints][H1]; [OS changes][V1]; [local probe's config-version note][L1] |
| What performance did this project observe? | **Local observation.** The probe reports a 5,000-domain list, 22/22 listed/www forms blocked and 10/10 controls loaded in both Safari and Chrome, with "no visible slowdown". This is functional evidence on one iPadOS version, not a latency benchmark, processor profile, database ceiling, or production-relay test. Its server-down results also establish dependence on cached verdicts and fail-open/fail-closed configuration. | [Local probe][L1] |

## Open questions

1. **Individual-account distribution and any extra entitlement approval.** Generate/inspect an actual distribution profile for the team's app ID and obtain Apple's answer if the capability is unavailable. Public entitlement enablement instructions and successful development signing do not resolve team-specific production approval.
2. **Authenticated registration terms.** Inspect the current CloudKit Identity & Trust form for fields or conditions beyond the eleven published checklist items, account eligibility, service-use categories, region availability, quotas/fees, approval turnaround, and ongoing availability obligations. The public console fetch reached Apple sign-in. Old request forms and forum authors' experiences are not substitutes.
3. **The exact development bypass predicate.** Apple explicitly documents development signing/Xcode installation, but the exact dependence on `get-task-allow`, installation mechanism, and OS version needs a direct Apple statement or controlled comparison. `DEBUG` is not evidence.
4. **Settings and removal protection on shipping builds.** Test disabling/removing the URL filter through Settings with and without device passcode/Screen Time restrictions, deleting the app, and the relevant individual/child Family Controls authorization modes. Determine whether any documented management restriction protects the URL-filter configuration itself. The existing local probe observed only the installation passcode and passcode-free in-app disable.
5. **Production hosting and cost.** Measure actual URL datasets, Bloom memory, shard layout, query/evaluation-key sizes, compute and issuer CPU, concurrency, cache hit/expiry behavior, relay latency, and behavior during service/issuer failure. The published tuning examples omit hardware and cannot settle production fleet size.
6. **A server-free product architecture.** Apple's published NEURLFilter design does not establish an entirely on-device PIR deployment as supported. Ask Apple about any proposed alternative topology before treating it as a production route. A remotely reachable gateway in front of a private backend is a narrower possibility than an unregistered loopback-only server.
7. **Version compatibility.** Validate 26.x, 27.0-27.2, and the announced 27.3 changes against the intended minimum OS and shipping protocol. Preserve older-client issuer endpoints as needed. Do not enable assumptions about the postponed Apple-infrastructure config-fetch behavior.
8. **Coverage beyond the probe.** Other browsers, non-WebKit/non-URLSession stacks, and in-app web views need their own evidence. Participation API adoption is a condition of coverage outside Apple's automatic networking path, not something this blocker can assume.
